# Phase 2 of D47: a browser probe on Miguel's PC (Google Flights, Kayak)

*Design, 2026-10-24. Nothing built, nothing installed. Phase 1 (Ryanair's fare finder on GitHub,
the link to the seller, the per-source comparison) is D47. Miguel decides when phase 2 starts.*

## Why a probe at home, and only there

The agencies Miguel wants to compare with (eDreams, Booking Flights, Kiwi, Gotogate, Mytrip)
have no price API for a site like ours and sit behind bot walls; the one place that compares
them all live is a metasearch page (Google Flights, Kayak, Skyscanner). From GitHub's runners an
automated browser is caught within hours, and keeping it alive means stealth plugins, proxies
and captcha solving: the barrier circumvention D47 forbids. From Miguel's own PC, with his
residential IP and a real Chrome profile, a browser doing a few dozen searches an hour is what
those sites expect from a person comparing fares, which is Miguel's own argument ("tou apenas a
verificar os preços mais baratos"). The probe therefore runs **only on a machine at home**, and
it behaves like a person: one tab, human pacing, no parallel searches, and it stops at the first
captcha instead of solving it.

## What it does

- **Input:** the hot list the pipeline already computes, published to R2 as `probe/wanted.json`
  by `run_airlines`' successor step (D47's rotation plus the open promotions' trips, with the
  route rules); the probe never decides what to search on its own.
- **Search:** for each (origin, destination, departure, return) in `wanted.json`, open the
  metasearch result page in a visible Chrome (Playwright, `channel="chrome"`, a persistent
  profile under `%LOCALAPPDATA%\pontonomada\probe\`), wait for the results, read the cheapest
  nonstop fare per seller from the DOM, and move on after a human-like pause (randomised, tens of
  seconds). Order: Google Flights first (stable URL parameters, no login, consent once), Kayak
  second (tolerates a real browser at human pace), Skyscanner only if the first two leave a gap
  (it is the most aggressive with automation, even for real browsers).
- **Output:** `probe/results/<run>.json` in R2 (a write-only R2 token scoped to `probe/`), one
  record per (trip, seller): price, currency, seller name, the page's own "updated" time when
  shown, our read time, the URL searched. Never a screenshot of a logged-in page, never cookies.
- **Stop rules (the same spirit as D47's `blocked`):** a captcha, a "press and hold", an
  "unusual traffic" page or an empty result three times in a row ends the run and writes
  `probe/state.json` with `paused_until` (24 h) and the reason. The probe never retries around
  it, never changes its user-agent, never routes through a proxy.
- **Pipeline side:** a new source per engine (`google_flights`, `kayak`), read from
  `probe/results/` on every run by a step after `run_airlines`: observations like any other
  (`source`, `gate` = the seller the engine showed, `found_at` = our read time, `deep_link` = the
  seller's own page only when the engine exposes a plain URL, else none). D47's rules carry over
  unchanged: a probe observation can be a comparison ("Também visto · Kayak via eDreams · 41 €")
  and a hot signal; it becomes a **deal** only when a source we can recheck (the airline's own
  site or the cache) confirms the trip, because the recheck must happen where the link goes and
  the probe is not always on.

## What Miguel must have

- A PC at home that stays on when the probe should run (his desktop, or any small always-on
  machine), with Chrome installed; the probe uses a profile of its own, not his personal one.
- Python 3.12+ and Playwright (`uv run playwright install chrome` is not needed: the system
  Chrome is used), installed once by a runbook in `docs/runbooks/`.
- Windows Task Scheduler: one task every 30 minutes at :05 and :35 (between the Worker's ticks,
  so a run's results are read by the next pipeline run), "run only when the user is logged on"
  so the browser can render.
- An R2 API token restricted to the bucket's `probe/` prefix (write) and `probe/wanted.json`
  (read), stored in the PC's `%APPDATA%\pontonomada\probe.env`, never in the repo.

## Open decisions (Miguel)

1. Start with Google Flights only, or Google Flights and Kayak from day one?
2. Does a probe-only price ever go public on its own (no), or is it always "Também visto" next
   to a rechecked promotion (the design above)?
3. The pace: a run of 20 searches at 30–60 s apart is 10–20 minutes every half hour. Fewer, more
   often, or a smaller hot list for the probe than for Ryanair?

## Not in this design

Skyscanner's and Kayak's own APIs (closed to us, research §2.6), any scraping API vendor (Miguel
pays for no API), running the probe anywhere but at home, and any technique that hides the probe
from the sites (D47's line).
